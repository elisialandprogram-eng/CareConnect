You are working on the payment system of this application.

IMPORTANT:
- Do NOT preserve backward compatibility.
- Historical bookings/payment records do NOT need to be supported.
- Do NOT keep legacy fields, routes, calculations, fallback logic, or duplicate payment paths merely for compatibility.
- We want a clean canonical payment architecture.
- You have authority to modify database schema, migrations, backend, frontend, services, APIs, tests, and related code.
- Do not use sub-agents.
- Do not stop after identifying issues. Audit and FIX every issue you find.
- Do not make superficial synchronization fixes. Replace the underlying architecture where necessary.

==================================================
PRIMARY OBJECTIVE
==================================================

Create ONE canonical payment lifecycle for an appointment.

The same booking must have exactly one authoritative payment state regardless of whether it is viewed by:

- Patient/client
- Provider
- Admin
- Backend services
- Notifications
- Emails
- Reports
- Earnings
- Settlement
- Refund logic

No screen or backend route may independently derive payment truth from multiple competing fields.

The architecture must distinguish:

Payment state
Appointment lifecycle state
Provider earnings state
Provider settlement state
Provider payout state

These are related but are NOT the same state.

==================================================
CURRENT PROBLEMS TO ELIMINATE
==================================================

The existing system contains overlapping authorities such as:

- payments.status
- appointments.payment_status
- appointments.payment_method
- payments.payment_method
- appointments.refund_status
- appointments.refund_amount
- payments.refund_status
- payments.refunded_amount
- provider_earnings.status
- legacy provider earning fields
- wallet transaction state
- provider wallet state
- provider ledger state
- payout request state

There are also duplicated implementations for:

- Wallet appointment payment
- Stripe payment
- Refunds
- Automatic cancellation refunds
- Offline payment confirmation
- Provider earning creation
- Payment completion fallback
- Payment state resolution in frontend screens

Eliminate these competing authorities.

STEP 2 — CANONICAL PAYMENT MODEL
==================================================

Create one canonical appointment payment aggregate.

A booking should have ONE canonical payment record/aggregate.

The canonical payment must contain the information required to determine:

- Payment method(s)
- Payment state
- Total payable amount
- Amount paid
- Amount remaining
- Amount refunded
- Amount refundable
- Currency
- USD settlement amount where required
- Provider transaction/reference IDs
- Failure information
- Dispute information
- Refund information
- Timestamps
- Idempotency information

Use clear names.

Do not keep duplicate fields merely because the old schema had them.

==================================================
STEP 3 — PAYMENT ALLOCATIONS
==================================================

The system MUST support multiple payment sources for one booking.

Do NOT model mixed payments using a single payment_method field.

Create/use a canonical payment allocation structure.

Example:

Booking total:

100 USD

Payment allocations:

Wallet = 30 USD
Stripe = 70 USD

Payment state:

PAID

Another example:

Wallet = 30
Stripe = 70

Refund = 50

Refund allocation:

Wallet = 30
Stripe = 20

Final payment state:

PARTIALLY_REFUNDED

The system must never choose the refund source simply because a wallet transaction exists.

Refunds must be allocated against the actual payment allocations.

==================================================
STEP 4 — CANONICAL PAYMENT STATE MACHINE
==================================================

Create ONE payment state machine.

Recommended states:

pending
processing
partially_paid
paid
failed
refund_pending
partially_refunded
refunded
disputed
cancelled

Every payment state transition must go through one canonical service.

For example:

transitionPayment()

or an equivalent clearly named canonical service.

No route, webhook, cron, wallet service, appointment service, or admin endpoint may directly mutate the canonical payment state.

All transitions must be:

- Validated
- Transaction-safe
- Idempotent where appropriate
- Auditable
- Deterministic

Invalid transitions must fail clearly.

STEP 5 — PAYMENT METHODS
==================================================

All supported payment methods must use the same lifecycle.

Supported methods currently include:

- Stripe/card
- Wallet

- Bank transfer

==================================================
STEP 6 — STRIPE PAYMENT FLOW
==================================================

Implement one canonical Stripe appointment-payment flow.

It must support:

- Checkout creation
- Processing state
- Successful payment
- Failed payment
- Expired checkout
- Retry
- Refund
- Partial refund
- Dispute
- Webhook idempotency

Stripe webhooks must go through the canonical payment service.

A Stripe webhook must not directly manipulate unrelated payment state fields.

On successful Stripe payment:

canonical payment state becomes appropriate paid/partially_paid state.

The appointment lifecycle must then be updated through the appropriate appointment lifecycle mechanism.

Do NOT let appointment completion itself magically mark an unpaid Stripe payment as paid.

Payment confirmation must come from the payment system.

==================================================
STEP 7 — WALLET PAYMENT FLOW
==================================================

There must be ONE canonical wallet appointment-payment implementation.

Remove duplicate wallet payment routes/logic.

Wallet payment must:

1. Validate balance.
2. Lock the wallet appropriately.
3. Create the wallet transaction.
4. Create/update the payment allocation.
5. Transition the canonical payment state.
6. Be idempotent.
7. Roll back atomically if any step fails.

For mixed wallet + Stripe:

Wallet amount must be recorded as one allocation.

Stripe remainder must be recorded as another allocation.

If Stripe fails, the wallet allocation must be handled correctly according to the payment transaction policy.

Do not leave money permanently deducted because a later payment step failed.

==================================================
STEP 8 — CASH AND BANK TRANSFER
==================================================

Offline payment must have an explicit lifecycle.

For example:

pending
→ receipt confirmation
→ paid

Only authorized provider/admin users may confirm receipt.

The confirmation must go through the same canonical payment transition service.

Do not allow appointment status changes to silently mark an offline payment as paid.

Clearly distinguish:

Appointment can be confirmed

from:

Payment is paid

from:

Appointment is completed

==================================================
STEP 9 — REFUNDS
==================================================

Create ONE canonical refund service.

All refunds must use it.

This includes:

- Patient cancellation
- Provider cancellation
- Admin refund
- Automatic stale appointment cancellation
- Stripe refund webhook
- Reschedule rejection refunds
- Wallet refunds
- Mixed wallet + Stripe refunds

The refund service must:

1. Validate refundable amount.
2. Determine payment allocations.
3. Refund each payment source correctly.
4. Update canonical payment state.
5. Record refunded amount.
6. Be idempotent.
7. Prevent double refunds.
8. Update appointment payment projection if one exists.
9. Emit the appropriate event.

For mixed payments:

Wallet refund must refund wallet.

Stripe refund must refund Stripe.

Never refund only the first payment source found.

Store the relevant dispute information.
